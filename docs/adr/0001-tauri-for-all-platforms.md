# ADR 0001 — Tauri 2 for all platforms

- Status: accepted
- Date: 2026-10-09

## Context

Selis targets Android, iOS, Windows, macOS and Linux from one codebase, with a small team.
The PDF canvas is web-native either way (PDFium compiled to WebAssembly), and we need a native
core for files, SQLite and, later, peer-to-peer transfer.

Alternatives considered (docs/SPEC.md, "Stack και PDF engine"):

- React Native / Expo + Tauri: two UIs to maintain.
- Flutter: cannot share the web PDF engine; foreign stack for the studio.
- Native per platform: five UIs.

## Decision

One Tauri 2 app (`apps/app`) for every platform: React + TypeScript UI in the system WebView,
Rust core in `crates/*`, typed IPC generated by tauri-specta.

Pinned to the **2.11** line (crate 2.11.6, CLI 2.11.5, `@tauri-apps/api` 2.11.1,
plugin-dialog 2.7.3, plugin-fs 2.5.2). Note: `tauri` 2.11.6 accepts `tauri-runtime(-wry)` 2.12
by semver but does not compile with it, so the runtime/macros/codegen/utils/plugin crates are
locked to their 2.11-era versions in `Cargo.lock`.

Security posture: strict CSP without remote sources, per-platform capabilities with least
privilege, app commands deny-by-default (declared in `build.rs`), the asset protocol scoped to
`$APPDATA/library/*.pdf`.

## Consequences

- One UI, one engine; layouts adapt per form factor (PhoneShell, TabletShell, DesktopShell).
- Mobile performance depends on the system WebView → validated by the P0 spike (docs/spike-p0.md).
- iOS cannot be built on Windows: `gen/apple` is generated and built on macOS CI runners.
- Upgrading Tauri means moving the CLI, JS packages, plugins and runtime crates together.
